# Team 12 handoff and roadmap

## Shared project claim

The fixed Company A file records independent machines. It has no verified
stage route, queue, waiting time or finished-line throughput. Our observed
branch reports machine health and forecasts. Our **virtual line** supplies
the known stage order and queues needed to test bottleneck detection and
bounded control. Keep these claims distinct in every slide and viva answer.

## Suggested ownership

Assign one owner and one reviewer to each workstream. If the team has fewer
members, combine roles; every member should still be able to run the demo
and explain the limits.

| Workstream | Owner's deliverable | Reviewer verifies |
|---|---|---|
| Data | `docs/DATA_AUDIT.md`, `src/clean.py`, baseline and replay | Raw file unchanged; 300 s modal gap; duplicate slot coverage never exceeds 100%; no made-up queue labels |
| IoT integration | MQTT broker, Node-RED flow, SQLite and dashboard | `scripts/check_demo.py` passes; bad records enter `rejected_records` only |
| Analytics and ML | Rolling metrics, machine baseline, 30-minute model and advisory | Explain Ridge, boosted trees and neural network; validation selects winner before held-out test; live features match offline origin |
| Virtual line and control | Simulator, bottleneck rule, bounded commands, acknowledgements | Healthy run sends 0 commands; slowdown identifies Stage 2; action comparison uses identical arrivals |
| Presentation and integration | Run sheet, screenshots, model/line result slides, viva rehearsal | Each person can explain observed vs simulated data and demonstrate one live change |

## Order of work

1. **Baseline:** Run `python tests/test_logic.py` and
   `python src/scenario_compare.py`. Save the output before editing
   thresholds.
2. **Integration:** Run `python scripts/run_demo.py --once --speed 1000`,
   open `http://localhost:1880/ui`, then run
   `python scripts/check_demo.py`.
3. **Actuation:** Run the normal slowdown demo long enough for virtual
   time to exceed 11,400 s. Confirm a command, accepted acknowledgement,
   and dashboard update. After the run, use
   `python scripts/check_demo.py --require-command`.
4. **Quality gate:** Run `python scripts/run_demo.py bad --once --speed 1000`
   and then `python scripts/check_demo.py --require-rejected`. Check
   `logs/nodered.log` for SQLite errors.
5. **Evidence:** Use `results/SCENARIO_RESULTS.md` for the before/after
   line figures and `results/MODEL_RESULTS.md` for forecast scores. These
   files are generated by scripts and should match the final slides.
   The analytics owner should present all three model families, the
   validation ranking, the held-out test and why the winner is used live.
6. **Rehearsal:** Each member explains one source of data, one decision
   rule, one test, one limitation and one safe modification from
   `docs/LIVE_MODIFICATION_GUIDE.md`.

## Demo sequence

- Show live observed machines with timestamps, coverage and alarms.
- Show a forecast and its explicit recommendation. This is advice about
  the recorded machine; it is not a command to a real actuator.
- Show the simulated line queue at Stage 2, the control message and ack.
- Show the no-action versus action comparison on identical arrivals.
- Show the bad-record mode and explain why a rejected event cannot affect
  the rolling metric.

## Questions to settle with the faculty

Because the fixed dataset has no real line route or queue observations,
ask whether the clearly labelled virtual line satisfies the control part
of Team 12's brief. Show `docs/ASSUMPTIONS.md` and the live architecture
when discussing this. Do not claim the simulated throughput gain occurred
at the factory.
